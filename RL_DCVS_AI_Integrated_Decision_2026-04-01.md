## 4) Candidate Model Ranking (for runtime DVFS)
Scoring dimensions: safety, offline suitability, online robustness, deployment complexity, sample efficiency.

1. Discrete CQL (Conservative Q-Learning) + runtime safety shield
- Rank: 1 (recommended)
- Why:
  - matches discrete action space (192 DCVS actions)
  - strong for offline logs and out-of-distribution control
  - safer than naive Q-learning/PPO in high-risk runtime control
- Risks:
  - needs broader behavior dataset (multi-action coverage)

2. Discrete IQL (Implicit Q-Learning) + runtime safety shield
- Rank: 2
- Why:
  - robust with unknown/implicit behavior policy
  - simpler and stable in many offline-control tasks
- Risks:
  - still limited by poor action coverage in dataset

3. Hybrid: Offline value policy + contextual bandit online adapter
- Rank: 3 (as enhancement layer)
- Why:
  - fast runtime adaptation to scene/temperature drift
  - can be constrained by safety rules
- Risks:
  - extra system complexity and monitoring requirement

4. Existing online tabular Q-learning (current baseline)
- Rank: 4
- Why:
  - easy to run and explain
  - useful as baseline/fallback
- Risks:
  - coarse state abstraction, weak generalization

5. Offline PPO on logged dataset (current script path)
- Rank: 5 (not preferred as mainline)
- Why:
  - can train from logs, implementation already exists
- Risks:
  - off-policy mismatch and instability for fixed logged trajectories

## 5) Final Model Selection
Final choice for production direction:
- Primary policy: Discrete CQL (offline trained)
- Runtime execution: Safety-constrained action filter + hysteresis
- Optional online adaptation: lightweight contextual bandit on top of safe action set

Reason for final choice:
- best balance among safety, offline learnability, runtime controllability
- directly fits current DCVS discrete action mapping
- easier to control regressions vs pure online exploration

## 6) Runtime Decision Logic (recommended)
1. Aggregate state in 2-5s windows (mean + percentile + trend).
2. Query CQL policy for top-k candidate actions.
3. Apply safety filter:
- FPS guardrail (block aggressive down-clock when FPS risk is high)
- thermal/power guardrail
- action step-size and dwell-time constraints
4. Apply one action and observe reward/guardrail violations.
5. Optional: bandit chooses among safe top-k candidates.
